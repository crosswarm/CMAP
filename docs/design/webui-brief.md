## 一句话

给研发团队用的多 Agent 任务管理台：**人只在授权闸口和最终验收上出现，不再当任务的传递者。**

## 背景：要消灭的动作

四类 AI Agent（规划、开发、备选、实机验证）协作完成研发任务。目前交接靠人：

```
Claude 出方案 → 人肉转交文档 → Codex 跑真机 → 写结果 → 人肉告知路径
  → Claude 读结果 → 不满意 → 人肉再转交 → …（人始终在传递环里）
```

后端已经把这个循环自动化了（任务派发、证据校验、评审、自动返工全部跑通）。**WebUI 的职责是让人能看懂正在发生什么，并在该拍板的地方拍板。**

## 使用者

研发负责人和工程师。不是普通消费者——**信息密度要高**，但不能变成一屏看不懂的表格。他们的典型动作：

- 早上打开看：昨晚那个 Mission 跑到哪了？卡住了吗？
- 收到通知：有个高风险操作等我批
- 验收时：这个"通过"的结论，证据在哪？可信吗？
- 出问题时：返工三轮了还没过，到底卡在哪条标准上？

## 五个核心场景

### 1. Mission 创建与跟踪
一个 Mission = 一个目标 + 约束 + **机读验收标准**（如"首屏 P95 ≤ 1800ms"）。系统自动分解成 Task DAG 并执行。用户要能看到实时进度与依赖关系。

### 2. 审批闸口（最关键）
高风险动作挂起等人批。**有两类授权，互不蕴含，绝不能合并成一个"批准"按钮**：

| 类型 | 例子 |
|---|---|
| `controlled` 受控副作用 | 给 Agent 发消息、触发定时任务、控制网关 |
| `mutating` 代码/配置变更 | 改源码、提交、合主干、删配置 |

批了前者不等于放行后者。审批时要能看到：谁请求的、为什么、附带哪些证据、什么时候过期。

### 3. 证据浏览
每个结论都可下钻到原始 Artifact，并沿**血缘关系**追溯（"这份指标对比派生自前后两次测量"、"第二轮 trace 取代了第一轮"）。证据带 sha256，由控制面独立复算过。

### 4. 返工追踪
评审判"不满意"时会自动派生后继任务。用户要能看清：
- 现在是第几轮
- 卡在哪条验收标准上（有具体的期望值 vs 实测值）
- 与上一轮比**有没有进展**（系统有确定性判定，不是主观感觉）
- 两道刹车的状态：轮次预算还剩多少、是否已判定无进展

### 5. Agent / Runner 健康与资源占用
哪些 Agent 在线、哪些真机被占用、锁什么时候过期。

## 最容易做砸的地方：长任务的状态表达

**一个 Mission 可能跑几小时到几天，其中大部分时间它是"正常但非活跃"的。**

系统区分了这些状态，UI 必须把它们表达出来，**不能都显示成转圈**：

| 状态 | 含义 | 用户该有的感受 |
|---|---|---|
| `RUNNING` | Agent 正在干活 | 正常，等着 |
| `WAITING_RESOURCE` | 真机/租户被别人占了 | 正常排队，不是出错 |
| `APPROVAL_REQUIRED` | **等我批** | 该我动了 |
| `INPUT_REQUIRED` | 缺信息 | 该我动了 |
| `REWORK` | 这轮被打回，已派生新任务 | 关注但不用动手 |
| `FAILED_TERMINAL` | 彻底失败/已升级 | 要看了 |

"等资源"和"等我批"在视觉上必须**一眼可分**——前者用户什么都不用做，后者卡在用户身上。

## 技术约束

- 后端 REST + **SSE 实时推送**（不是轮询）
- 前端 React + Vite
- 跨公网多租户，最终部署 Linux 服务器
- 认证走 OIDC

## 希望你产出

1. **2-3 个信息架构不同的方案**（不是配色不同），各自说明适合什么使用节奏
2. 每个方案的导航结构与页面清单
3. **Mission 详情页**的高保真设计（这是主战场）
4. **审批中心**的设计——重点解决"两类授权不能混"这个约束怎么在视觉上成立
5. 关键交互流：审批、返工追踪
6. 状态设计：loading / 空 / 错误 / **长时间等待**各自怎么表达
7. 明确取舍：每个方案牺牲了什么
