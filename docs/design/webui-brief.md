## 2026-09-20 实现接线补充

- Mission 列表已改为直接按租户查 Mission；尚未派生 Task 的目标也会显示。
- 事件流：`GET /v1/missions/:id/events`，使用 EventSource 监听 `mission-event`。
  SSE 只含事件元数据，收到后按需重新读取当前 Mission/Task/Review/Evidence/Approval。
  重连会完整回放，按 `data.event_id` 去重；不要把重复事件显示成重复动作。
  SSE 连接成功只表示连接正常，不能据此显示 Agent 在线或任务完成。
- 当前 API 仅监听本机，租户来自控制面配置；尚未实现 OIDC，不得宣称多用户身份认证完成。
- React/Vite 前端尚未实现；以下方案分析和交互约束均为设计，不代表可用产品。

### 2026-09-21：Mission 创建接线

创建页可调用 `POST /v1/missions`，输入见 `schemas/mission-create.v1.schema.json`：
目标、机读验收、显式风险、返工预算，以及为本次用户提交生成的 request_id。
双击或网络重试必须复用原 request_id 和原输入；409 提示请求内容冲突，
503 表示启动未确认，保留原键重试；202 后按 mission_id 打开详情并订阅 SSE。
输入变成新目标时才换新键。不要让浏览器填写 owner/tenant 或提交“已完成”状态。
当前执行模板只有 inspect/v1 的单任务返工闭环，DAG 自动规划仍未实现。
开发代理须保持 API 的同源写入约束，不通过放宽 CORS/Host 绕过；正式前端可与 API 同源托管。

### 三个原型方案的取舍

| 方案 | 导航与主页面 | 适用节奏 | 牺牲与约束 |
|---|---|---|---|
| acceptance-ledger | 左侧任务队列/审批收件箱；详情优先验收表，再证据血缘与任务交接，右侧审批 | 负责人每天集中验收、优先处理需本人决策的任务 | 验收依据清楚，但宽屏信息多；小屏要将证据、返工拆成详情视图。作为默认方向 |
| chronicle-workspace | 顶部任务/任务流/审批/证据/资源；任务流以交接时间轴和选中事件详情为中心 | 工程师追查某次交接、返工从哪一步开始 | 因果和时间顺序突出，但跨轮次指标比较要另进验收页，不作为默认验收首页 |
| mission-command-map | 左侧 Missions/审批/证据/Agents；详情以角色泳道、任务依赖和侧边任务信息为中心 | 多 Agent 并行执行时定位依赖与责任人 | 大图适合排障，不利于批量验收；删除底部重复 DAG，只保留一个依赖视图。当前未实现的 Agent/Runner 健康不能以示例替代 |

### 双 scope 同时待批的交互约束（待前端验证）

审批中心分别显示 controlled 和 mutating 的独立卡片，保留各自请求 ID、动作、
原因、证据及到期时间。卡片入口写“查看并决定 controlled / mutating”，不在列表
直接放两个相邻的最终批准按钮。进入单个审批详情后，再显示“仅批准该 scope”与拒绝。
确认对象固定为所选审批 ID 和 scope；提交期间禁用当前卡片，完成后留在结果页，
不自动跳到下一个请求，也不把另一 scope 的按钮移到刚点击的位置。
每次处理另一 scope 都要重新进入其详情；不提供“全部批准”。

验收必须覆盖：两项同时 pending、连续双击、请求失败后重试、其中一项已被处理、
SSE 重连回放。实际“双 pending”界面和点击验证仍未交付，不能用这段说明代替。

## 一句话

给研发团队用的多 Agent 任务管理台：**人只在授权闸口和最终验收上出现，不再当任务的传递者。**

## 背景：要消灭的动作

四类 AI Agent（规划、开发、备选、实机验证）协作完成研发任务。目前交接靠人：

```
Claude 出方案 → 人肉转交文档 → Codex 跑真机 → 写结果 → 人肉告知路径
  → Claude 读结果 → 不满意 → 人肉再转交 → …（人始终在传递环里）
```

后端已经把这个循环自动化了（任务派发、证据校验、评审、自动返工全部跑通）。**WebUI 的职责是让人能看懂正在发生什么，并在该拍板的地方拍板。**

## 使用者

研发负责人和工程师。不是普通消费者——**信息密度要高**，但不能变成一屏看不懂的表格。他们的典型动作：

- 早上打开看：昨晚那个 Mission 跑到哪了？卡住了吗？
- 收到通知：有个高风险操作等我批
- 验收时：这个"通过"的结论，证据在哪？可信吗？
- 出问题时：返工三轮了还没过，到底卡在哪条标准上？

## 五个核心场景

### 1. Mission 创建与跟踪
一个 Mission = 一个目标 + 约束 + **机读验收标准**（如"首屏 P95 ≤ 1800ms"）。系统自动分解成 Task DAG 并执行。用户要能看到实时进度与依赖关系。

### 2. 审批闸口（最关键）
高风险动作挂起等人批。**有两类授权，互不蕴含，绝不能合并成一个"批准"按钮**：

| 类型 | 例子 |
|---|---|
| `controlled` 受控副作用 | 给 Agent 发消息、触发定时任务、控制网关 |
| `mutating` 代码/配置变更 | 改源码、提交、合主干、删配置 |

批了前者不等于放行后者。审批时要能看到：谁请求的、为什么、附带哪些证据、什么时候过期。

### 3. 证据浏览
每个结论都可下钻到原始 Artifact，并沿**血缘关系**追溯（"这份指标对比派生自前后两次测量"、"第二轮 trace 取代了第一轮"）。证据带 sha256，由控制面独立复算过。

### 4. 返工追踪
评审判"不满意"时会自动派生后继任务。用户要能看清：
- 现在是第几轮
- 卡在哪条验收标准上（有具体的期望值 vs 实测值）
- 与上一轮比**有没有进展**（系统有确定性判定，不是主观感觉）
- 两道刹车的状态：轮次预算还剩多少、是否已判定无进展

### 5. Agent / Runner 健康与资源占用
哪些 Agent 在线、哪些真机被占用、锁什么时候过期。

## 最容易做砸的地方：长任务的状态表达

**一个 Mission 可能跑几小时到几天，其中大部分时间它是"正常但非活跃"的。**

系统区分了这些状态，UI 必须把它们表达出来，**不能都显示成转圈**：

| 状态 | 含义 | 用户该有的感受 |
|---|---|---|
| `RUNNING` | Agent 正在干活 | 正常，等着 |
| `WAITING_RESOURCE` | 真机/租户被别人占了 | 正常排队，不是出错 |
| `APPROVAL_REQUIRED` | **等我批** | 该我动了 |
| `INPUT_REQUIRED` | 缺信息 | 该我动了 |
| `REWORK` | 这轮被打回，已派生新任务 | 关注但不用动手 |
| `FAILED_TERMINAL` | 彻底失败/已升级 | 要看了 |

"等资源"和"等我批"在视觉上必须**一眼可分**——前者用户什么都不用做，后者卡在用户身上。

## 技术约束

- 后端 REST + **SSE 实时推送**（不是轮询）
- 前端 React + Vite
- 跨公网多租户，最终部署 Linux 服务器
- 认证走 OIDC

## 希望你产出

1. **2-3 个信息架构不同的方案**（不是配色不同），各自说明适合什么使用节奏
2. 每个方案的导航结构与页面清单
3. **Mission 详情页**的高保真设计（这是主战场）
4. **审批中心**的设计——重点解决"两类授权不能混"这个约束怎么在视觉上成立
5. 关键交互流：审批、返工追踪
6. 状态设计：loading / 空 / 错误 / **长时间等待**各自怎么表达
7. 明确取舍：每个方案牺牲了什么

# 第 2 轮反馈（2026-08-09）

三个方案 × 两轮迭代已收到，入库在 `docs/design/prototype/`。两条硬约束都成立：
授权不合并（`mutating` 画成常驻的"未请求"占位、按钮写"仅批准 controlled"，比要求更进一步——
让**没被授权的那类持续可见**，而不是隐藏）；等资源与等我批一眼可分（左栏按"要不要我动手"分组，
`WAITING_RESOURCE` 配"正常排队 · 无需操作"）。

选型倾向 **acceptance-ledger** 打底：它把验收标准表放在第一屏，而"人只在最终验收上出现"
要求验收是第一位公民。`mission-command-map` 的泳道图作为详情页的一个视图 tab 保留，
但底部的"任务依赖 DAG 概览"与主区泳道是同一份数据画两遍，可以砍。

## 必须补的两件事

### 1. 两类授权**同时** pending 的那一帧

三张图里 `mutating` 全是"未请求"。真正危险的是两者同时待批——那时两个按钮竖着排，
"不能合并"这个约束在视觉上还成不成立？这是审批中心唯一必须画对的帧，恰好没画。

要一并说明：靠什么防止连点误批（空间分隔？二次确认？还是强制先处理其中一类）。
判据是**手滑不能造成越权**，而不是"标签写清楚了"。

### 2. 每个方案的说明文档

只有 PNG，信息架构的取舍看图猜不出来，选型容易凭观感定。每个方案一份 md：
导航结构与页面清单、适合什么使用节奏、**牺牲了什么**。

## 后端字段现状——界面只能显示后端真有的东西

上一轮的设计里有若干元素后端给不了。逐条对齐：

| 界面元素 | 状态 | 界面该怎么处理 |
|---|---|---|
| 模型 / 努力度 + 设置来源 | **已实现** | 见下方契约。`effort` 有例外，务必读完 |
| 「已送达 · 已确认」双态 | 后端只有"已送达" | 设计是对的，缺口在后端。**保留这个区分**，后端会补——它正是"握手 ≠ 完成"的界面表达 |
| 「队列位置 2 · 预计 ≈18m」 | **不存在** | 锁拿不到就进 `WAITING_RESOURCE`，没有队列、没有位置、没有 ETA。先只显示"正常排队 · 无需操作"，位置与 ETA 留位不填 |
| 「证据完整性：verified (sha256)」 | **未复算** | schema 强制了 sha256 格式，但控制面从未独立复算。改成「sha256 已登记」，`verified` 徽章等复算落地后再上 |

最后一条是 brief 上一版的措辞误导（"由控制面独立复算过"是写了但没做），按实现照画没有错。
但按现状显示 `verified` 会变成假信号，和容器 `Up`、端口 `LISTEN`、进程 `rc=0` 同一性质。

## 新增契约：`execution_policy.model_policy`

已落地到 `schemas/task-envelope.v1.schema.json`，UI 可以按这个形状取值：

```jsonc
"model_policy": {
  "model":  "gpt-5.6-sol",              // 派发时解析出的最终值
  "effort": "low|medium|high|xhigh",    // 统一抽象档位，各家由 Adapter 映射
  "source": "agent_default|task_override"  // UI 显示"继承 Agent 默认"还是"本 Task 覆盖"
}
```

三点约束：

- **整个对象可缺省**。缺省表示沿用 Agent 自身默认，UI 显示为"未指定"，
  不要替它编一个默认档位——那会让人以为控制面覆盖了它其实没碰的设置。
- `source` 是**派发时的快照**，不是读取时回算的。Agent 默认值可能在派发后被改，
  回算会得出错误结论。
- **`effort` 目前不得呈现为"已生效"**。实测 codex v0.144.6 + gpt-5.6-sol：
  `low` 与 `xhigh` 跑同一道推理题，token 消耗 22,024 vs 21,997，差异在噪声内；
  且 codex 连 TOML 语法错误的 `-c` 值都不报错，所以"命令成功"证明不了配置被采纳。
  `model` 是确证生效的。在拿到 effort 的生效证据前，界面上它是一个**已记录但未确认生效**
  的意图，不是一个开关。可以让用户选，但不能显示成"当前正以 xhigh 运行"。

# 第 3 轮：后端补齐（2026-08-25）

派发链路接上了真 Agent。控制面现在能无人值守跑完一次 Mission：派发 → codex 真实执行
→ 收结果落账本 → 逐条核对验收标准 → 独立复算证据哈希（实测 46-102s）。
对界面来说，下面几条改变了「能显示什么」。

## 可以画了

| 界面元素 | 变化 |
|---|---|
| 「证据完整性：verified (sha256)」 | **现在有依据了**。控制面在 Adapter 层独立复算文件哈希，对不上即判失败，不采信 Agent 自报。徽章可以上 |
| 验收标准逐条结果 | 结果落账本，含 `actual` 与 `passed`。**漏答等同未通过**——Agent 没回应的标准会被判失败，界面要能表达「没答」而不只是「没过」 |
| 证据 id | 由控制面分配，形状是 `任务id:角色`。Agent 自称的名字（常是 `report`）不进账本——它会撞车 |

## 必须分开表达的两种终局

后端现在把它们记成两个事件，界面不能混：

| 事件 | 含义 | 用户该做什么 |
|---|---|---|
| `MISSION_FAILED` | 结果不达标，验收没过 | 看结论和证据，决定要不要重来 |
| `MISSION_ESCALATED` | 预算耗尽或判定无进展 | **等你来救**，系统已经不再自动重试 |

之前所有非完成状态都被记成 `MISSION_ESCALATED`，包括刚开始跑——那是个假的求救信号，
已修。这条与「等资源 vs 等我批」是同一类要求：**看一眼就知道要不要我动手**。

## 返工追踪页现在有真数据了

自动返工已接进主流程。界面能拿到的形状：

- **第几轮**：任务通过 `supersedes_task_id` 串成链，第 N 个就是第 N 轮
- **卡在哪条标准**：`review-decision` 的 `failed_criteria` 逐条带 `expected` /
  `actual` / `reason`，并指向具体证据 id。**「Agent 没回应这条」与「实测没达标」
  措辞不同**，界面要能分辨——前者要追的是 Agent 没干活，后者是没干成
- **有没有进展**：由确定性程序比对相邻两轮（证据哈希、失败标准集合、指标、
  错误指纹），不是主观感觉
- **两道刹车还剩多少**：`stop_conditions.max_additional_cycles` 是预算，
  当前轮次从任务链长度得出

## 仍然给不了

- 「队列位置 · 预计 ETA」依然不存在（锁拿不到只有 `WAITING_RESOURCE`）。
- 「已送达 · 已确认」双态依然只有「已送达」。

## 审批闸口现在有真数据了

- controlled / mutating 任务派发前自动创建对应 scope 的 pending Approval。
- 任务处于 `APPROVAL_REQUIRED`、Mission 处于 `AWAITING_APPROVAL` 时，binding 为空，
  说明 Agent 尚未启动；界面可据此明确显示「卡在你这里」。
- API 批错 scope 返回 409；两类授权互不蕴含。他租户审批不可见也不可决策。
- 正确批准后事件流出现 `APPROVAL_GRANTED` 并继续 `TASK_STARTED`；拒绝后 Task 为
  `REJECTED`、Mission 为 `FAILED`。
