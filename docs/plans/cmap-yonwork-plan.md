## RALPLAN-DR

Principles: actual remote terminal proof; one effect per immutable attempt; no invented authority/identity/evidence; reuse transport and control-plane gates; honest isolation limits.
Drivers: cancellation under lease loss, precise correlation/idempotence, real structured evidence without leaking conversations.

Options:

1. **Installed Host CLI, owned run, explicit allowlisted abort** (preferred). Reuses Host discovery/auth and caller idempotency, narrowly parses vendor SSE. Costs a dedicated bounded stream parser and exact Host abort workaround; version drift must fail closed.
2. **Direct Host HTTP client**. Easier stream control and request bodies, but duplicates discovery/token handling and increases credentials/redirect attack surface. No current need justifies replacing the working CLI.
3. **OpenClaw agent CLI**. Good documented agent/session controls and message-file input, but automatic embedded fallback can duplicate an uncertain Gateway operation, and it lacks documented caller-selected idempotency keys. Reject for this execution path unless a future version proves fallback can be disabled before effects.
4. Existing diagnostic summary only is not viable: hashes/event counts cannot prove TaskResult or remote stop. Do not market this as a working Adapter.

## Scope and contract

- Add a YonWork adapter with all SPI methods and opt-in Worker registration. Route identity is `yonwork:<configured-agent-id>` and must be explicitly frozen in the Task's preferred_agent, with no alternative profile fallback. Default worker behavior remains unchanged. Require a dedicated configured `cmap-*` Agent, never silently main/business/default; no Agent/account configuration changes during startup.
- Advertise only `yonwork.validate`, `execution_level: B`, no session resume, and **no worktree isolation**. Chat execution accepts `controlled` only; `mutating` does not imply controlled. Reject lower-risk chat dispatch, unsupported model policy, non-report evidence roles, and explicit forbidden requirements the Host cannot enforce before sending.
- Reuse existing controlled approval before dispatch; no second fake authorization file, no synthetic human identity in live runs, and no Jev-to-human impersonation. Jev advice can support technical choices but cannot fabricate a grant. Local unit/fixture tests remain autonomous. Live setup/approval must be concrete and reviewable before any missing human authority is requested.
- Extend mission-plan node contract with optional `yonwork: {chat_send:true, policy_sha256:<64-hex>}`. For yonwork.validate this block and explicit profile route are required. Materializer maps the request bit to existing `permissions.yonwork.chat_send=true` and freezes the policy hash in input parameters. The bit is a permission request, not approval. The approval reason displays the profile ID, policy hash, no-delivery/report-only scope and task goal. Post-approval changes conflict with immutable task input; changing the configured runtime target or verified policy rejects dispatch.
- Real execution requires a read-only observation of the selected Agent's effective Gateway policy, with no available tools and matching hash. Agent-list metadata, config.get disk snapshots and handwritten attestation are insufficient. Use the packaged CLI's fixed `tools.effective` RPC (`operator.read`), returning only selected identity/tool inventory/notice fields and a canonical policy hash. Runtime selection must be cross-checked against current Host Agent metadata; never guess a default Gateway, extract/copy credentials, or expose full config. Require exact agent identity, empty effective tool inventory and no unresolved MCP catalog notices. If proof is unavailable, health is unavailable and send refuses.
- tools.effective rejects unknown session keys (tools-effective-DNs36xaT.js:343). Operator setup therefore provides a dedicated empty baseline session for the selected profile, without a model run. Its effective policy supplies the approval pin. After approval/lease checks and durable dispatch intent, the sole claimant may prepare its exact owned empty attempt session using only fixed `sessions.patch` with `key` (no model, routing override, messages, history, profile/config mutation). Observe tools.effective for that exact attempt session and compare its canonical profile/tool-policy hash to the approved pin BEFORE chat.send. Session preparation is part of the explicitly described controlled lifecycle; it is included in intent/crash tests and never implicitly grants a chat or mutating authority.
- Use canonical `agent:<normalized-cmap-agent-id>:explicit:<cmap-digest>` per tenant/owner/mission/task/attempt, with strict normalized profile ID validation and exact returned identity checks. Never global/main/channel sessions; `deliver=false`, `attachments=[]`. No originating channel, model override, arbitrary API path or account settings from envelope/model output. Operations on a recovered binding must also match this Adapter's configured runner ID and profile; never query/cancel another runner's Host.
- Preserve a stable request/idempotency key derived from the immutable attempt. Use the documented Gateway run identity to keep cancellation possible before acknowledgment. Confirm received run IDs against the expected key and exact session. Concurrent identical starts coalesce; different immutable inputs for the same key conflict; no fallback resend after uncertain acceptance. Existing ledger bindings suppress redispatch after worker restart; absent in-memory state is uncertainty, not a new send.
- Add an optional side-effect-free `prepareBinding(envelope,ctx)` SPI method for deterministic external identities. YonWork must implement it; other adapters retain their current flow. Add `Store.claimTaskBinding` in both stores: atomic null-to-binding CAS, legal QUEUED/WAITING_RESOURCE → RUNNING transition and metadata-only TASK_DISPATCH_INTENT event in one transaction; returns whether this caller claimed it. Same-binding replay is a no-op, conflicting binding rejects. Reuse the binding column, no extra intent table/state. RUNNING means the control-plane attempt is active, not Host acceptance. A later matched Host ACK adds metadata only, not a second state transition. This keeps crash recovery compatible with RUNNING→VERIFYING/FAILED_TERMINAL.
- Shared dispatch order for prepared bindings: select/preflight adapter; verify Task is eligible and exact controlled Approval is approved/unexpired; verify frozen profile/permission/policy; verify actual active `yonwork:host` lease matches task + runner + resource + expiry; compute and atomically persist binding/intent; only the winning caller may invoke startTask once. After CAS and session preparation, recheck Task state, permission/profile/policy hash, approved/unexpired scope and actual lease immediately before chat.send. Wire this check through an optional DispatchContext pre-send callback owned by the control-plane dispatch function; YonWork refuses to send without it. Returned binding must equal the prepared one. A crash after intent but before send sacrifices liveness and escalates uncertainty on recovery; it never resends. A failure after Host acceptance retains identity for scoped cancellation. Existing non-prepared Codex/Kimi flow remains compatible.
- Remote binding records the expected run ID and dedicated session (remote_context_id), protocol/version and control-plane runner ID. Do not consume model self-identification. A Host mismatch cannot redirect cancellation to another run.
- Keep only bounded in-memory wire buffers and sanitized event metadata. Strict UTF-8/SSE framing, exact supported event names and exact run/session matching; ignore unrelated events without logging bodies. Only a correlated Gateway envelope inside chat.message or gateway:chat-message with state final/error/aborted proves remote terminal state. Host chat.error, chat.complete, handshake, delta, EOF, CLI failure/exit and abort ACK alone ALWAYS keep terminal_observed=false. Never infer terminal from text or Host's broad stopReason predicate.
- CLI interruption/early close without terminal proof remains uncertain. No blind retransmit or unscoped history read. The exact global event wrapper may be used only as a short-lived, owned-run-filtered cancellation observer if the direct stream is gone. Start it before the abort request and wait for its documented startup handshake so terminal events cannot race subscription.
- Cancellation uses the existing CLI's generic entry point only for the hard-coded `/api/chat/abort` POST and exactly own `{sessionKey,runId}`. No generic passthrough is exposed. Always start an owned-run-filtered global observer and confirm its handshake before abort, even if direct SSE is open. Bound all CLI/observation work within the existing 5-second grace and retain leases when unconfirmed. Killing a local CLI is cleanup only, never evidence of remote cancellation.
- Require declared `yonwork:host` resource lock AND prove actual ownership at the shared dispatch boundary before any Host send. DAG owns acquisition/renewal/release; declared-only, wrong task/runner, expired or lost leases refuse dispatch, including non-DAG invocation paths. This deliberately serializes local YonWork CMAP tasks because Host tool/workspace isolation is not confirmed. It cannot exclude manual/outside-CMAP use (ADR-0004 residual risk). Narrow per-host/profile resource identities belong to P4 once multiple runners are admitted.
- Metadata/health probes must run asynchronously in a child process, not call the existing spawnSync probe inside the Worker event loop and starve lease heartbeats. Reuse the sanitized probe and current runtime-directory selector, extracting the selector only if needed for both consumers; no manual token discovery or new credential store.

## Structured output and evidence

Define `schemas/yonwork-output.v1.schema.json` first and codegen its type. Reuse existing status/summary/criterion-result semantic fields, with no task/tenant/owner/run identity or model-selected filesystem paths. Expected output is one strict JSON final reply; no code-fence/prose repair. Do not accept partial assistant output or an aborted final-looking JSON fragment.

The local report artifact is explicitly a **captured structured provider reply**, not an invented remote file or proof of a business operation. Write only validated response fields into a fixed report path in the task's physical workdir, atomically/no overwrite/symlink rejection; independently read/hash those bytes through the existing normalizer and synthesize control-owned artifact references. Unsupported additional evidence roles fail before send. Hard metrics are recomputed by the existing gate; real validation scenarios must independently verify their own expected observations. No raw transcript, prompt echo, delta stream or credentials enters repo/audit artifacts.

Input artifacts are real transferred data: read each reference through existing readVerifiedArtifact using ctx.worktree and a mandatory SHA, once; require valid UTF-8, aggregate at most 32KiB, stable ordering. Embed the same verified bytes as named/role/hash-tagged untrusted text in a provider-specific prompt. Never forward local URIs or fetch arbitrary URLs. Reject binaries, oversize, missing/tampered files or unsupported code-worktree context before sending. The shared prompt's local-file-writing instructions are not compatible and must not be reused here.

The shared recordResultArtifacts path in workflows/activities.ts selects captured-reply handling from the control-owned YonWork binding/capability, never an Agent-supplied flag: classification restricted, conservative contains_secrets=true / contains_pii=true, and provenance.content_assessment="unassessed". These are protective handling flags, not a claim that a detector found particular data. Do not reuse the generic false/false clean claim for unassessed model content. No deterministic scanner is presented as proof of absence. This first capability validates reply-derived observations/text inputs; evidence of a real business operation requires an independent observation and cannot be manufactured by wrapping an assertion in a report.

## Pre-mortem and test plan

- **False completion or cross-run capture:** Host stream-close/early unrelated event looks terminal. Tests feed interleaved runs/sessions, missing IDs, misleading complete names, Unicode/chunk splits, complete-without-final, and abort partials; only exact owned final can produce completed evidence.
- **Duplicate work or escaped cancellation:** stream drops after send or wrapper exits; retry/abort-only shortcut misfires. Real fake-CLI counters prove one send per stable key; crash matrix covers before intent, after intent/before send, and after Host ACK/before state update. No uncertain recovery resends. Same-session wrong-run abort is refused; abort ACK without terminal retains leases; timeout/cancel process cleanup does not fabricate remote success.
- **Authority/evidence drift:** unsafe profile silently used or model writes arbitrary artifact paths/identities. Tests prove opt-in agent selection, scope gate, unsupported restrictions refusal, schema rejection, fixed physical output paths/no symlinks, no sensitive sentinel in normalized errors/events, and fresh independent hash checks.

Unit: pure SSE reducer + strict output/identity validation. Integration: real fake CLI scripts and actual Memory/Pg control-plane paths with explicit synthetic test authority. E2E: actual dedicated YonWork session after applicable approval, structured result and abort with terminal proof. Observability: only event kind/time/correlation/terminal state/hash, no transcript. Detailed case list is in the test-spec artifact.
