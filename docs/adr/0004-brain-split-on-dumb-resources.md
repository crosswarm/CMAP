# ADR-0004：哑资源的脑裂防护——为何不用 fencing token

- 状态：已接受
- 日期：2026-08-03
- 来源：架构评审 `pdf-cmap-arch-review`

## 背景

CMAP 用 `ResourceLock` 保护三类独占资源：真机设备、YonWork 测试租户、Git worktree。锁带 TTL，runner 崩溃后过期，新 runner 可抢占。

问题场景：runner A 持有真机锁 → 网络分区 → 控制面判定锁过期 → runner B 抢占 → **但 A 其实还活着并仍在操作真机**。两个 runner 同时认为自己独占，操作互相干扰，而各自的证据都会显示"成功"。

评审时的初始结论是引入 **fencing token**（单调递增的令牌，被保护资源拒绝低于已见最大值的操作）——这是分布式锁的标准解法。

## 决策

**不使用 fencing token。改用「锁续租 + runner 侧失锁自停」。**

## 为什么 fencing token 在此不成立

fencing token 的前提是**被保护资源本身能够校验令牌并拒绝过期持有者**。CMAP 的三类资源全都做不到：

| 资源 | 操作方式 | 能否校验 token |
|---|---|---|
| 真机设备 | codex 的 computer-use 点击屏幕 | ❌ 设备完全不知道 CMAP 存在 |
| YonWork 租户 | `yonworkctl chat send` | ❌ CLI 无 token 参数，Host 不参与协议 |
| Git worktree | 文件系统读写 | ❌ 文件系统不做此类校验 |

它们都是**哑资源**——没有任何一处能拒绝一个"过期持有者"的操作。

给 `ResourceLock` 加 token 字段只会在账本里留下一个**从未被检验的字段**，同时制造"脑裂已经防住了"的错觉。这比不加更危险：错觉会让人停止寻找真正的防线。

## 采纳的方案

**防线放在唯一能执行它的地方——runner 自己。**

1. **续租**：runner 持锁期间必须周期性调用 `renewLock`（如每 30s，TTL 设为 90s）
2. **如实失败**：`renewLock` 在锁已释放、已过期被抢占或不存在时**必须返回 `false`**，绝不静默成功
3. **失锁自停**：runner 收到 `false` 即认定自己已失去独占，**主动终止正在进行的操作**

第 2 条是关键契约，已写入 `Store.renewLock` 的接口注释并由契约测试固化。静默成功会让 runner 误以为仍持有独占——那就退回到了脑裂。

## 残余风险（必须如实记录）

这个方案**不能根除脑裂**，只能缩小窗口：

- 从"失锁到 runner 察觉"之间仍有最长一个续租周期的窗口
- runner 进程完全卡死（无法执行自停逻辑）时，防线失效
- 网络分区期间 runner 无法续租，会主动停止——这是安全的方向（宁可停工不冒险），但会造成误停

**兜底手段**：两个 runner 同时操作会产生互相矛盾的证据（时间戳交错、状态不一致）。评审环节应能检出并判定该轮无效。这是事后补救，不是预防。

`docs/threat-model.md` 中已记录"哑资源的独占无法从技术上根除"这一残余风险。

## 后果

- `Store` 新增 `renewLock(lockId, newExpiresAt): Promise<boolean>`
- runner 实现必须包含续租心跳与失锁自停逻辑（P4 实现 runner 时落实）
- 不再考虑给 `ResourceLock` 加 fencing token，除非将来接入的资源**确实支持**条件写（例如某个提供 CAS 语义的设备管理 API）

## 一般化的教训

引入某个标准解法前，先确认**它的前提在本系统中是否成立**。fencing token 是分布式锁的正确答案，但它假设被保护资源是协议参与方。当资源是"哑"的时候，这个假设不成立，照搬只会得到账面安全。
